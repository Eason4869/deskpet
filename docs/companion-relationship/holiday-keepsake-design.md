# 节日纪念卡 H1：万圣节首批

用户于2026-10-25新增要求：除关系阶段卡之外，节日可解锁特殊纪念卡；首批使用现有万圣节特殊服饰，卡面具有万圣节元素。这是新功能，不把解锁/存储混入当前F3视觉修订。原定卸载、日常内容接入、搜索、全量测试与EXE/ZIP验证仍继续，仍不做MSI。

## 用户流程与解锁默认规则

- 伙伴主页的纪念册提供“关系纪念”和“节日纪念”两个明确入口，计数来自已保存记录。切换只改变展示，不切伙伴、不加好感。
- 现有 `HolidayCalendar` 将万圣节定义为本地10月31日一天。沿用其Occurrence/InstanceKey，不再维护第二份节日日历。
- 在活动日期内，用户**实际看到当前伙伴**或打开其主页，且该伙伴具有可信、Ready、可读取的对应万圣节服饰时，尝试获得本年度节日卡。后台启动/隐藏窗口/单纯扫描日历/测试预览不触发。
- 唯一身份为稳定伙伴ID + 节日Occurrence.InstanceKey，每伙伴每年一张。切换回来、重启、重复事件和时区/时钟回拨均不能重复领取。记录本地日期、UTC及偏移；拒绝早于已观察日期水位的倒退补领。不声称离线系统能验证真实世界时钟。
- 不要求额外好感度，也不改变既有装扮解锁的彩蛋规则。获得卡片不授予永久装扮；卡中呈现活动服饰与衣柜解锁是两个明确结果。免打扰下静默保存并在主页可见，不新增自动弹窗或TTS。
- 非活动日期可查看本年度万圣节预览，明确显示“尚未解锁 / 10月31日与伙伴见面”，不能导出成已获得纪念卡。预览不写入解锁记录，不修改系统时间，不落盘纪念文件。
- 不从旧的HolidayActivityState推断历史获卡，因为其中部分记录在后台刷新时产生，不能证明实际相处。启用新系统后开始记录。
- 不支持该服饰的导入伙伴明确说明暂无适配节日卡；不套用别的伙伴造型、不硬编码按显示名称匹配。

## 首批实际资源与纪念表达

仓库 `assets/holidays/catalog.json` 已有五位Ready官方伙伴：e-bao / dafeiyu / marfu / xiaobei / gugugaga；OutfitId为halloween-2026。选取必须通过当前可信伙伴身份与现有HolidayCatalog匹配，使用该OutfitDefinition捕获的OpenPreview来源及版本，不拼接用户提供路径。

万圣节卡保留F3的800×480构图与可读性：人物用真实节日立绘；标题“万圣节相伴纪念”；年份、获得日期与伙伴名；纪念短句例如“把这个万圣节，留在我们的相伴记忆里。”不编造一起做过的具体事件。卡片作为独立导出图片应完整成立。

视觉采用主题明确的南瓜灯、蝙蝠、糖果或古堡剪影，集中在人物背景/边角，避免遮盖姓名、日期和台词。万圣节的紫灰、暗红和少量南瓜橙与服饰配合；浅主题保持浅色卡体，深主题卡面与页面区分。**禁止回到用户已否定的无意义装饰圆圈、绕人物的圆弧和乱放星形。** 有主题含义的南瓜图形不是替代排版的装饰。使用项目原有服饰资产和原生矢量，不下载外部角色图，不生成替代官方服饰。

节日结束后仍能查看和保存已获得卡。重新安装服饰或更新资源不能悄悄改变旧纪念中的造型。已获得卡的伙伴名称、服饰标识/版本、年度与获得时间在领取时冻结；卡面可以随当前语言和浅深主题重新渲染，但一次打开的预览/保存使用同一PNG字节。

## 数据、图像与故障边界

- 新建独立共享纪念数据，不修改关系积分账本schema，也不改既有HolidayState/衣柜。建议`data/commemorations/holiday-state.json`和同目录portrait blobs，沿用项目原子替换、进程间租约与严格版本检查模式。
- 保存记录包括稳定伙伴ID、节日ID/Occurrence.InstanceKey、节日年份、获得LocalDate/UTC/offset、捕获姓名、可信角色ID、OutfitId/Version、肖像SHA256及受控blob名。未知版本/坏文件保留原样并阻止覆盖；界面显示实际保存失败/重试。
- 领取时保留**真实服饰透明肖像**的只读快照，后续移除资源仍可渲染同一造型。只保存有界、已验证PNG（现有preview规格480×520，限制字节数及解码尺寸），不是外部任意路径。blob按哈希命名，目录受控、拒绝重解析逃逸。不要在预览未获卡时持久化。
- 事务顺序为安全暂存/持久化blob，再原子发布引用它的记录；记录成功才显示解锁。发布失败不虚报获卡，安全保留已有数据；允许未被引用的自有blob暂存，不为此引入广泛清理器。并发重复领取只产生一个逻辑记录，且不会丢失其他伙伴的记录。
- 写入属于DataMaintenanceGate实际活动，必须可排空；清空聊天、恢复默认偏好、清理缓存、更新及卸载全部保留新纪念数据。不能在UI线程等待存储或在独占维护时绕过门禁。
- 缺失/损坏的已保存肖像显示可理解错误，不替换成普通服饰假装原卡，也不影响其他卡/整个主页。可读的原始记录仍保留。PNG读取、异常回退和Bitmap生命周期与F3同等严格。

## 工程边界与实施拆分

**H1a 共享解锁与持久化：** 小型只读定义/record/快照、日历资格判断、稳定去重、原子blob与记录存储、异步协调和维护排空。Framework与portable覆盖同一规则；先证明并发/失败/未来版本/时钟回拨/数据保留，再交接确切API。不得在此伪造UI解锁或跨端重写规则。

**H1b 实际入口与节日卡面：** 两端真实伙伴显示及主页入口接入H1a；伙伴主页纪念册分类、未解锁预览/已获列表/错误重试；对应服饰肖像和万圣节图案；保存与预览一致、主题切换和资源移除后保留。沿用F3静态图像/排版帮助类，不重做已有关系卡。

依赖顺序为F3审阅通过 → H1a → H1b → M5c2 → S1 → S3 → M6。每项独立审阅，不并行修改产品。规则/UI新增可见文字13语言，字面量camelCase键。只使用自有测试数据，日期通过测试时钟注入，不修改主机日期或真实用户状态。

验收至少包含：10月30日/31日/11月1日边界，真实可见/主页访问与后台区别，每伙伴每年度去重、跨年、重启/时区/回拨、同身份换装与独立导入隔离、关闭反馈/免打扰、失效资源及存储失败、并发写入与维护租约、未知版本保留、服饰卸载后旧卡可导出、浅深/长语言/窄宽/锁定预览不落盘。实际截图覆盖五位官方伙伴的万圣节卡和双主题；Windows非活动桌面、Avalonia无头、macOS硬件与安装包分别如实记录。

## 架构检查后的明确规则

已采纳只读 builder check 的边界：可用的对应节日服饰即可获卡，不要求当时实际穿着，也不要求开启自动节日换装。最早活动年度为2026，后续年度沿用日历；资源名中的2026不能代替活动年度判断。

日期水位在真实相处时推进，覆盖非节日和不支持节日服饰的伙伴，并在整个节日纪念存储中共享。预览、读取列表和后台刷新不推进水位。一次事件的本地日期由同一个UTC与偏移样本计算；真实时区倒退导致日期较水位早时同样保守拒绝新领，旧卡仍可读取。

失败重试重新检查当前时间、伙伴和资源资格，不建立跨日待补领队列。活动结束后尚未保存的卡不算已获得，界面如实说明；活动内已受理的真实相处可以在稍后完成。切换伙伴仅使旧界面回调失效，不撤销已发生的真实相处或将其归属改给新伙伴。

维护活动租约必须在任务入队之前获取，覆盖排队和实际写入，关闭时异步排空。PNG需要共享结构校验以及WPF/Avalonia各自完整解码和像素读取；固定上限4 MiB、480×520，保留原始透明PNG字节。状态JSON上限32 MiB，达到上限拒绝新增并保留旧记录，不自动删旧卡。单卡blob损坏与整个状态schema损坏分开处理，前者不阻塞其他卡。
